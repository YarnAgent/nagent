# ADR-0001: v0.3 — mesh peer trust, net-wide list, low-lag attach

- **Status**: Proposed
- **Date**: 2026-05-20
- **Deciders**: @funyarn (with Claude)

## Context

v0.2 (commit `83d8812`) shipped hub-and-spoke multi-node:

- A joiner can redeem an invite issued by an existing peer; both sides exchange long-term ed25519 pubkeys and write `authorized_keys` + `ssh_config` entries.
- `nagent attach <peer>/<session>` SSHes from the local node into the named peer and re-execs `nagent attach` there. Works only if the joiner's `authorized_keys` was wired for that peer (i.e., during the joiner's own redeem).
- `nagent list` shows the local tmux session inventory only.
- The bus (`SEND` / `RECV` / `SUBSCRIBE`) is local-daemon-only; cross-node delivery is unimplemented.
- Attach is plain `ssh -t … tmux attach`: every keystroke is a round-trip, so input feels laggy whenever RTT > ~50 ms.

Three concrete deliverables for v0.3:

1. **`nagent list` shows every session in the net**, not just local.
2. **Any node can attach to any session**, without re-inviting — true mesh trust, not hub-and-spoke.
3. **No perceived input lag during attach**, even on a high-RTT or lossy link.

This ADR records the chosen approach for each, plus the cross-cutting work (gossip, cross-node bus) needed to support them.

## Decision

### 1. Mesh trust via issuer-relayed gossip

After a successful redeem (`cmdJoinRespond`), the issuer fans out **on the joiner's behalf** to every other peer in the net. Mechanics:

- The issuer already has SSH trust with each peer (their `authorized_keys` contain the issuer's long-term pubkey from when each peer joined). No bootstrap problem.
- For each peer `P` in the net (excluding the issuer and the joiner), the issuer opens an SSH connection to `P` and runs a new command: `nagent gossip-add-peer`. The payload (sent on stdin, framed JSON):

  ```json
  {
    "v": 1,
    "netId": "n-…",
    "newPeer": {
      "nodeName": "…",
      "pubKey":   "<base64url raw32>",
      "addresses": ["host:port", …],
      "sshUser":  "…",
      "roles":    []
    },
    "ts": "2026-05-20T…Z",
    "sig": "<issuer signature over canonical(payload sans sig)>"
  }
  ```

- `nagent gossip-add-peer` on `P`:
  1. Reads the payload, verifies `sig` against the calling SSH key (which `P`'s authorized_keys already attests is the issuer's long-term pubkey, because that's the key that authed this very connection).
  2. Confirms `netId` matches `P`'s active net.
  3. Appends the new peer's pubkey to `P`'s `authorized_keys` (fenced + tagged like any other peer entry, idempotent — if the tag exists, skip).
  4. Adds the new peer to `P`'s local `peers.json`.
  5. Writes a small ACK to stdout (`{"v":1,"ok":true}`); no body on success-with-no-change.

- Fanout is bounded-concurrent (cap 8), best-effort: any peer that fails to receive the gossip is captured and retried by the **heal pass** below. The join itself does NOT fail if some peer is unreachable — the joiner is already trusted by the issuer and any peer reachable now, which is enough to attach to live nodes.

**Heal pass:** on daemon startup, each node looks at its peers list and, for any peer it cannot find in its own `authorized_keys` (or vice-versa — anyone in `authorized_keys` not in peers.json), it attempts a self-signed gossip push to reconcile. A `gossip-add-peer` payload signed by any peer that the receiver already trusts (per its peers.json) is accepted; this lets two nodes that were both offline during each other's joins heal as soon as they share a network with any third node.

**Trust model:** every peer in a net trusts the originator's pubkey (from `authority.json`, written during the net's creation) and every peer it received a signed gossip from. The signing key for normal joins is the issuer's; for heal passes it's the healer's. v0.3 keeps the chain one-deep (only direct peers can vouch); v0.4 may extend to multi-hop chains for federated trust.

**Why issuer-relay and not joiner-walk:** the joiner cannot SSH to existing peers immediately after redeem — those peers don't have the joiner's pubkey in their `authorized_keys` yet (chicken-and-egg). The issuer can, because it already has trust with everyone. Relaying through the issuer eliminates the bootstrap problem entirely; the joiner only ever talks SSH to the issuer during join.

### 2. Net-wide `nagent list` via parallel fanout

`nagent list` (no flags) returns sessions from every peer in the active net:

```
NODE                  SESSION         CREATED              ROLES
wsl26                 alpha           2026-05-20 14:46     -
wsl26                 test01          2026-05-20 14:46     agent-alpha
mac-m3                bravo           2026-05-20 23:42     -
dots-mac-mini         (unreachable)   -                    -
```

Implementation: the local daemon issues parallel `ssh peer 'nagent list --local --json'` invocations (one per peer in `peers.json`, capped at 16 concurrent), each with a 3-second timeout. Results are merged. Unreachable peers show `(unreachable)` instead of dropping silently — explicit failure is better than misleading completeness.

`nagent list --local` keeps the v0.2 behavior (local sessions only). `nagent list --net <netId>` works against a non-active net. JSON output via `--json` for machine consumption.

To avoid per-call SSH handshake cost when listing repeatedly, the local daemon reuses one OpenSSH `ControlMaster` connection per peer (5-minute `ControlPersist`).

**Why fanout-RPC rather than a gossip/cache:** sessions come and go on the order of seconds; a cached gossiped state would routinely be stale by the time the user sees it. Fanout pays one SSH RTT per peer (cheap on Tailscale: ~10–30 ms over the active path) and is always current. v0.4 may layer a short-lived cache (1 s TTL) once cross-node bus is in place, for `list`-heavy workflows.

### 3. Low-lag attach

Two new attach modes alongside the v0.2 default:

#### `nagent attach <peer>/<session>` (default — unchanged in v0.3)

Plain `ssh -t peer -- nagent attach <session>` (existing behavior). Best for low-RTT LAN where the v0.2 UX is already snappy. Documented as "good for LAN / Tailscale direct".

#### `nagent attach <peer>/<session> --line` (new — line-buffered shell)

Solves the "every keystroke round-trips" problem for shell-style sessions:

```
$ nagent attach mac-m3/alpha --line
nagent: connecting to mac-m3/alpha via bus (line mode)
[mac-m3:alpha] $ ls
total 48
…
[mac-m3:alpha] $ vim foo.py           # ← warns: "vim is TUI; use plain attach for full-screen apps"
```

- **Local readline**, with full GNU readline keybindings and history. The user's keystrokes never cross the network; the local terminal echoes them instantly.
- On `Enter`, the line is wrapped as `{verb: "SEND_KEYS", node, session, line}` and dispatched over the bus to the remote daemon. Remote runs `tmux send-keys -t <session> '<line>' Enter`.
- **Output streaming**: at attach time, the remote daemon installs `tmux pipe-pane -o -t <session>` to a per-session fifo that the daemon reads, framing chunks as `{verb: "PANE_OUTPUT", node, session, bytes}` and pushing them through the bus to the local subscriber. Local prints chunks above the prompt using readline's `redisplay`. Latency on output is unavoidable (cross-net), but **input** is instant.
- **Detection of TUI mode**: when the remote tmux pane reports its `alternate_screen` flag is set (i.e., a full-screen TUI is active), `--line` prints a warning and exits with a hint to use plain `attach`. We don't try to be a TUI proxy in line mode.
- **Detach**: `Ctrl-D` or a `/detach` line; the pane keeps running on the remote.

This is the user's preferred design ("type to shell, then send to session"). It's intentionally narrower than full attach: shell-and-CLI ergonomics over high latency, not a universal TUI proxy.

#### `nagent attach <peer>/<session> --mosh` (new — mosh transport, optional)

When the remote has `mosh-server` and the local has `mosh-client`, this mode shells out to `mosh chouchou@peer -- tmux -L nagent attach -t <session>`. Mosh gives us **predictive local echo** (handles full TUI input lag automatically) plus UDP transport (survives roaming). The nagent attach path just wraps it.

If `mosh` isn't installed, the command errors with an install hint and offers `--line` as an alternative. We do not auto-install mosh.

#### Auto-mode picking

`nagent attach <peer>/<session> --auto` (also the future default once stable) pings the peer's tailscale latency once; if RTT > 80 ms, suggest `--line` for shell or `--mosh` if available; otherwise plain `attach`. This is an opt-in UX hint; the user always picks the mode explicitly. v0.3 ships `--auto` as suggestion-only; v0.4 may make it the silent default.

### Cross-cutting: cross-node bus

`--line` requires the bus to actually deliver frames between nodes. v0.3 lands the minimum needed:

- Each daemon, on first need-to-talk-to-peer-P, opens a persistent multiplexed SSH channel: `ssh peer -- nagent bus-pipe`. `bus-pipe` is a constrained command that reads bus frames on stdin and writes outgoing frames to stdout, hooked into the remote daemon's local bus.
- Local daemon maintains one `bus-pipe` connection per active peer; idle connections close after 60 s.
- The `hops` field already in the v0.2 frame format increments at each forwarder; frames are dropped after `hops > 4` to prevent loops.
- For v0.3, routing is direct (no multi-hop forwarding): if A wants to send to C, A opens a `bus-pipe` to C directly. This works because mesh trust now gives A `authorized_keys` access to C. Multi-hop relay routing is deferred to v0.4.

This makes the cross-node bus a thin SSH-multiplexed transport; no new wire protocol beyond the existing framed JSON.

### Backward compatibility

- v0.2 invites without a `gossipKey` field are accepted; the joiner falls back to v0.2 hub-and-spoke behavior (no gossip walk). Once mesh trust is healed via daemon-startup heal passes, the joiner becomes indistinguishable from a v0.3-native joiner.
- v0.2 `nagent list` callers see the new net-wide output by default; they get the legacy local-only output via `--local`.
- The plain `nagent attach` path is unchanged for callers who don't pass `--line` / `--mosh`.

## Consequences

### Positive

- Any-to-any attach works without per-pair invites; new joiners get full mesh trust automatically.
- `list` reflects reality across the net, not just the local node.
- Shell-style remote work over high-latency links feels instant under `--line`.
- Cross-node bus unlocks future v0.4 work (broadcast, routing, multi-hop relays).
- No new external runtime dependencies (mosh is optional).

### Negative

- Gossip introduces new constrained SSH commands and a new signed-pass format — more surface area for auth bugs. Mitigated by reusing the v0.2 invite signature/state-machine pattern and front-loading review (see PR + `nagent-ssh-reviewer` agent).
- Fanout `list` is O(N) SSH connections at call time; on nets ≥ 50 peers this gets slow. v0.3 doesn't address this; v0.4 should layer a cached/gossiped view.
- `--line` is a non-trivial new UX (line-buffered shell shim with output streaming above a readline prompt). Edge cases: ANSI escape codes in command output, partial-line output, output during input. Will need user testing.
- The gossip-on-startup heal pass means a freshly-booted daemon hits every peer with a small SSH connection — fine for small nets, noisy for large ones. Cap concurrency and randomize jitter.

### Neutral

- Daemon's responsibilities grow modestly: it now manages per-peer SSH ControlMasters and a `bus-pipe` connection pool. This is incremental, not architectural.

## Alternatives Considered

- **Gossip via UDP/QUIC instead of SSH-piped frames**: lower latency, fewer connections, but introduces a new transport, new auth (we'd need TLS/Noise or signed datagrams), and Tailscale already gives us low-latency encrypted UDP under the hood when SSH is direct. Rejected for v0.3; revisit in v0.4 if perf matters.
- **Predictive echo built into nagent (mosh-style without mosh)**: gives full TUI low-lag attach without the mosh dep. Rejected: reinventing mosh is a multi-month project; users with mosh installed get the same outcome via `--mosh`.
- **List via bus broadcast cache**: each daemon broadcasts session deltas; every node maintains a CRDT-ish view. Better at scale, but requires the cross-node bus to be solid first and adds a cache-staleness UX problem. Deferred to v0.4.
- **Multi-hop bus routing in v0.3**: would let A→C even if A has no direct SSH trust to C, via B as relay. Rejected: mesh trust via gossip already eliminates the "no direct trust" case for v0.3's threat model (a single net of mutually-trusting peers). Multi-hop matters for federation, which is v0.5+.
