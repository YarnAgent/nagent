# ADR-0003: v0.5 — `nagent-relay` dumb-pipe TCP rendezvous + latency-aware multi-path routing

- **Status**: Proposed
- **Date**: 2026-05-22
- **Deciders**: @funyarn (with Claude)

## Context

v0.2–v0.4 assume every nagent node is on a Tailscale tailnet: peers reach
each other via `ssh nagent.<peer>` resolved to a `100.x.x.x` address. Two
real frictions surface in practice:

1. **Tailscale is a hard prerequisite.** A friend or a $3/mo VPS with sshd
   running cannot participate without installing tailscaled first. For "this
   is just a CLI tool" this is a high bar.
2. **Direct routing is sometimes far from optimal.** Tailscale falls back to
   its own DERP relays when WireGuard direct can't NAT-traverse. Those
   relays are outside our control and can be hundreds of ms away. The
   v0.4 `--line` mode + web Line-mode are *symptom mitigations* — they don't
   improve the path itself.

We want a path that works for any-to-any nagent reachability **without**
requiring Tailscale, while *preferring* direct paths when they happen to be
fast (e.g., LAN, healthy tailnet).

## Decision

Add `nagent-relay`: a small TLS-fronted dumb-pipe TCP rendezvous daemon.
Clients maintain a persistent TLS connection to one or more pinned relays
and ask the relay to "open a stream to peer X". The relay routes opaque byte
streams between two registered clients. **SSH stays end-to-end encrypted
across the relay**; the relay box never sees plaintext, never holds an
SSH key, and never participates in the SSH session.

Path selection is **node-local + Tailscale-DERP-style**: each node
periodically probes direct latency to peers + fetches each relay's STATUS
(per-registered-peer latency) and additively estimates `my→relay→peer`. On
`nagent attach`, `nagent` picks the lowest-latency candidate. A 10 ms
hysteresis (Tailscale's value) prevents flapping. A `--via auto|direct|<relay>`
flag is the manual override.

```
Node A (NAT)                    Relay (public IP / DDNS)         Node B (NAT)
   │                                  │                                │
   │ long-lived TLS:8443 ────────────►│◄──────────── long-lived TLS:8443│
   │  REGISTER(A, pubkey, sig)        │      REGISTER(B, pubkey, sig)  │
   │                                  │                                │
   │ OPEN dst=B, sid=42 ──────────────►│ ── OPEN src=A, sid=… ─────────►│
   │                                  │                                │ → localhost:22
   │ ◄══════════ DATA (opaque ciphertext, relay never decrypts) ══════►│
   │            ↑                                       ↑              │
   │   ssh handshake + session, end-to-end encrypted, relay is blind   │
```

## Wire protocol

Each frame is **length-prefixed binary**:

```
[ 4 bytes BE: total body length (verb + payload, capped 1 MiB + slack) ]
[ 1 byte: verb ]
[ verb-specific payload ]
```

### Verbs

| Verb | Hex | Direction | Payload |
|---|---|---|---|
| `REGISTER`        | 0x01 | C→R   | JSON `{nodeName, pubKey, nonce, sig, netId?}` — sig is ed25519 over the raw nonce bytes |
| `REGISTER_OK`     | 0x02 | R→C   | JSON `{relayName, version}` |
| `REGISTER_REJECT` | 0x82 | R→C   | JSON `{reason}` |
| `OPEN`            | 0x03 | both  | JSON `{streamId, dstNodeName?, srcNodeName?}` |
| `OPEN_OK`         | 0x04 | both  | JSON `{streamId}` |
| `OPEN_REJECT`     | 0x84 | both  | JSON `{streamId, reason}` |
| `DATA`            | 0x05 | both  | `[4 bytes BE: streamId][raw payload]` (no JSON) |
| `CLOSE`           | 0x06 | both  | `[4 bytes BE: streamId][optional JSON reason]` |
| `PING`            | 0x07 | both  | `[8 bytes BE: ts_micros]` |
| `PONG`            | 0x08 | both  | `[8 bytes BE: echoed ts_micros]` |
| `STATUS_REQ`      | 0x09 | C→R   | empty |
| `STATUS_OK`       | 0x0a | R→C   | JSON `{relayName, peers: [{node, rttMs, lastSeen}]}` |
| `CHALLENGE`       | 0x0b | R→C   | JSON `{nonce}` — server-issued 32-byte nonce; first frame after TLS handshake |

The handshake is: TLS → relay sends `CHALLENGE` → client signs `nonce` with
its long-term ed25519 key and replies `REGISTER` echoing the nonce + sig.
The relay verifies the sig, looks up `(nodeName, pubKey)` in the allowlist,
and replies `REGISTER_OK` or closes with `REGISTER_REJECT`.

`streamId` is **per-connection** and **per-direction**: each side allocates
its own. The relay maps `(srcConn, srcStreamId) ↔ (dstConn, dstStreamId)`.

### Auth

The relay challenges with a server-generated `nonce` (32 random bytes).
The client signs the nonce with its long-term ed25519 key (the same key used
across the mesh; see ADR-0001) and presents `{nodeName, pubKey, nonce, sig}`
in `REGISTER`. The relay verifies the signature and checks `(nodeName, pubKey)`
against its allowlist.

The **allowlist is a union** of:

- For every net the relay box has joined as a regular nagent peer:
  `~/.nagent/nets/<netId>/peers.json` (auto-refreshed every 60 s).
- Explicit grants in `~/.nagent/relay/allowlist.json` managed via
  `nagent relay grant <node> <pubkey>` on the relay box.

Replay protection: the nonce is server-issued; clients cannot pre-sign.
Connection state is also per-TLS-session, so a captured `REGISTER` cannot
be replayed against a different TLS session.

### Transport

TLS over TCP, default port `8443`. Self-signed RSA-2048 cert generated at
`~/.nagent/relay/{cert,key}.pem` on first run (5-year validity, SAN includes
hostname + reachable IPs + localhost). Clients pin via `nagent relay add
<url>`, which fetches the cert and prompts for fingerprint confirmation —
identical UX to `nagent web trust` from v0.4.

## Threat model

| Threat | Mitigation |
|---|---|
| Relay operator reads SSH traffic | Out-of-scope — SSH is end-to-end encrypted; the relay sees only ciphertext. |
| Relay impersonation (MITM) | Cert pinning at `relay add`; subsequent connections verify the pinned fingerprint, not the cert chain. |
| Replay of `REGISTER` | Server-generated nonce; bound to the TLS session. |
| Unauthorized peer registers | Allowlist check on every `REGISTER`. Allowlist is union of mesh peers + explicit grants. |
| Crossed wires between nets | `netId` in `REGISTER` namespaces the allowlist lookup. Same node name in two nets requires two pubkeys. |
| Stream exhaustion / DoS | Per-conn cap on outstanding streams (initial: 64). `OPEN_REJECT` once at cap. |
| Memory exhaustion via huge frames | `MAX_FRAME_LEN = 1 MiB + 32 B`. Decoder rejects oversized frames. |
| Slow consumer blocks others | TCP back-pressure per stream; v0.5 relies on kernel TCP buffers, revisited if it bites. |

## Out of scope (deferred to v0.5.x / v0.6)

- Multi-hop chains (`relay → relay → peer`). v0.5 single-hop only.
- Mid-session failover (transparent live migration). User reconnects on failure.
- HTTP-CONNECT / SOCKS frontends. JSON+binary framing only.
- Bandwidth / jitter / loss probing.
- STUN-style NAT traversal. If direct doesn't work, we just relay.
- Let's Encrypt cert provisioning (currently self-signed + pinning).
- systemd / launchd unit for the relay daemon (`/install-service` later).
- Gossip-based auto-discovery of relays (each client `relay add` for now).

## Consequences

**Wins.**

- Tailscale becomes **optional** — any sshd-running box anywhere can host a
  relay; any client behind any NAT can use it.
- Latency-aware routing replaces "Tailscale picked whatever it picked".
- Operator UX is small: one new daemon, mirrors `nagent web serve` design.
- No new long-running agents on regular peers (relay client lives inside
  the existing `nagent daemon` process tree).

**Costs.**

- New trust surface: each pinned relay is a piece of pinned config that
  needs to be added on every client. Mirrors `nagent web trust` from v0.4.
- Cert rotation is a manual `relay remove` + `relay add` on every client.
  Acceptable for v0.5; Let's Encrypt is a follow-up.
- Operator must keep the relay daemon running. Single point of failure for
  the routes that depend on it; mitigated by allowing multiple relays.
- Slight protocol surface: the binary frame format must be stable across
  client/server versions. Versioning is via `version` field in
  `REGISTER_OK`; clients that see an unfamiliar version error out cleanly.
