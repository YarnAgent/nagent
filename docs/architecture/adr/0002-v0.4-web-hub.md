# ADR-0002: v0.4 — `/web` browser access via a nagent-web hub

- **Status**: Proposed
- **Date**: 2026-05-21
- **Deciders**: @funyarn (with Claude)

## Context

v0.3 shipped CLI-only access to tmux sessions across the mesh: `nagent attach <peer>/<session>` for direct SSH, `--line` for low-lag shell mode, `--mosh` for predictive echo. Users now want to view (and interact with) sessions through a web browser without setting up SSH on the client.

Constraints we're working under:

- The mesh has 3+ nodes typically, on a Tailnet (Tailscale CGNAT). Nodes already share ed25519 long-term keys and `authorized_keys`-based mutual SSH trust.
- We do not want a per-session new auth system, nor a separate identity store.
- We do not want to require every node to run an HTTPS server with a public cert.
- "Multi-host distribution" is a stated requirement: not all sessions live on one node, and the design must reflect that.

Research summary (see PR description / research report):

- `xterm.js` 6 + WebGL renderer is the de facto frontend (VS Code, Theia, Hyper, ttyd, asciinema-player).
- `ttyd` (MIT, mature) is the canonical "PTY-in-browser" daemon and pairs trivially with `tmux attach`.
- `tmux pipe-pane` is **not** suitable for the browser stream — it emits text only, not the raw PTY byte stream (cursor moves, alt-screen, colors are lost). The ttyd-fronts-`tmux attach` path gives us a real PTY stream.
- Multi-host streaming patterns in production: (a) per-node server + discovery + browser redirect (asciinema, ttyd, ad-hoc), (b) central gateway with proxying (Coder, JupyterHub, VS Code Remote Tunnels), (c) WebRTC data channels (rare; overengineered inside an existing encrypted overlay like Tailscale).

## Decision

Add a **`nagent-web` hub** — a per-net opt-in HTTPS server that any node can run via `nagent web serve`. The hub owns:

- The HTTPS termination + the browser-facing site (xterm.js + a small SPA).
- Discovery of sessions across the net (reuses the existing `list_net.ts` SSH fanout).
- A WebSocket endpoint per session that bridges to `ttyd` running on the session's actual owner node.

Browsers only talk to the hub. Other peers do not need to expose HTTPS or run a web server. The hub reaches peer sessions on demand using the **existing v0.3 SSH mesh trust** — no new auth surface, no long-lived agent connections to babysit.

```
                 ┌─────────────────────────────────────────────────────┐
                 │                                                       │
   browser ─https─► nagent-web hub ─ssh tunnel─► peer A (on demand)      │
                       │                          ├── ttyd --interface 127.0.0.1
                       │                          └── tmux -L nagent attach -t <sid>
                       │
                       └─ssh tunnel─► peer B (on demand)
                                       └── ttyd … tmux attach …
```

### Hub side

- New subcommand: `nagent web serve [--port 4443] [--bind 0.0.0.0]`.
- Idempotent: starts the hub if not running; prints the URL otherwise.
- On first run: generates a **self-signed ed25519 cert** at `~/.nagent/web/cert.pem` + `key.pem`. CN includes the node's hostname and Tailscale IPs.
- Serves:
  - `GET /` — the SPA (xterm.js + session list).
  - `GET /api/sessions` — net-wide session inventory, computed via the existing `list_net.ts` fanout. Each entry includes `{ node, name, sessionId, url: "/s/<node>/<name>" }`.
  - `GET /s/<node>/<name>` — page that opens a WebSocket to `/ws/<node>/<name>`.
  - `WS  /ws/<node>/<name>?t=<token>` — proxies bytes to the peer's ttyd. **Read-write by default**; `?readonly=1` (or a token claim) restricts.
- New file: `~/.nagent/web.json` — port, HMAC secret for token issuance, last-served pid.

### Peer side (no permanent state change)

When the hub gets a `/ws/<node>/<name>` request:

1. Verify the HMAC token (see auth below).
2. Resolve the peer via `nagent.<node>` ssh_config alias (same as `nagent attach`).
3. Open an SSH connection to the peer with **Unix-domain socket forwarding** (OpenSSH 6.7+: `-L /tmp/nagent-hub-<id>.sock:/tmp/nagent-ttyd-<id>.sock`).
4. On the peer, exec: `"$SHELL" -ilc 'ttyd --interface unix:/tmp/nagent-ttyd-<id>.sock --writable -t titleFixed=<name> tmux -L nagent attach -t <name>'`.
5. Bridge browser WebSocket ↔ tunneled socket.
6. On WebSocket close: tear down the SSH tunnel. ttyd exits when its socket closes; tmux session keeps running (just detaches that ttyd client).

The peer does not need any new state. It does need **ttyd installed**; the installer documents this as a `/web`-feature soft dep.

### Authentication

Two layers:

1. **Cert pinning** for the HTTPS handshake. On the client, `nagent web trust <hub-url>` fetches the hub's cert fingerprint, prompts the user to confirm, and pins it under `~/.nagent/web/known_hubs.json`. The user's browser still shows a "self-signed" warning the first time; the user clicks-through once and the browser caches it.
2. **HMAC-signed bearer tokens** for `/ws/*`. Token minted by `nagent web token --session <node>/<name> [--expires 1h] [--readonly]`, signed with the hub's HMAC secret. Token carries a single-session scope, expiry, and a r/w flag. Token sits in the URL query (`?t=…`); the WebSocket handshake re-validates on each open.

We are **not** adding OIDC, magic-link, or built-in user accounts in v0.4. Token URLs are the auth bearer; they're not safe to paste in public chat. A future v0.5 can layer in OIDC behind an optional reverse proxy.

### Why "pull from hub" not "push from peers"

We considered the alternative where peers open long-lived outbound WebSockets to the hub on startup and register their sessions (VS Code Remote Tunnels / Cloudflare Tunnel pattern). Rejected for v0.4 because:

- It introduces a new always-on connection per peer to maintain. The hub becomes a SPOF that takes everyone offline when it restarts.
- We already have a working SSH mesh; reusing it via on-demand tunnels is one fewer new protocol.
- Cold-start latency on first browser hit is the only downside (≈ one SSH handshake + a ttyd launch, ~300-500 ms over Tailscale). After the first hit, the SSH ControlMaster keeps the tunnel warm.

If users later want browser access to peers behind NAT that can't accept inbound SSH from the hub, push-mode is the natural extension and lands as v0.5.

### Multi-hub topology

Any node can become a hub by running `nagent web serve`. A net can have zero, one, or many hubs:

- **Zero hubs**: `/web` is simply unavailable. CLI continues to work.
- **One hub**: typical home setup. The hub is a long-lived box (server / always-on Mac); other peers (laptops) come and go.
- **Many hubs**: each hub independently serves its own URL; they share no state. Browsers connect to whichever hub the user picked. Useful for redundancy or for users who want different hubs in different network contexts.

Hubs do not gossip about each other. A `webHubs` field could be added to `peers.json` later as an opt-in advertisement; v0.4 keeps hub URLs as out-of-band knowledge.

### Lifecycle

- `nagent web serve` — start hub (idempotent).
- `nagent web stop` — stop hub. Doesn't affect CLI / daemon / running tmux sessions.
- `nagent web token --session <node>/<name>` — mint a URL.
- `nagent web trust <hub-url>` — pin hub cert on a client.
- `nagent web sessions` — same as `/api/sessions` but on the CLI.

Per-session ttyd processes are ephemeral: spawned per WebSocket, killed when the WebSocket closes. No long-lived background ttyd pool to manage.

## Consequences

### Positive

- Single URL for browser users (no per-node URL juggling, no per-node TLS).
- Zero new long-lived connections; relies on the v0.3 SSH mesh.
- Works through NAT for the **hub** (you point browsers at the hub's address); peers only need outbound… wait, peers need to accept *inbound SSH from the hub*. That's an explicit constraint of "pull from hub" — see Negative below.
- ttyd is MIT, mature, and one static binary; no maintenance burden on us.
- xterm.js + WebGL gives modern terminal UX (truecolor, fast scrollback, links, sixel later).
- Multi-host story is real: hub fans out via the same `list_net.ts` we shipped in v0.3.

### Negative

- Hub-bound bytes: all browser traffic routes through the hub. A laptop browsing a session on a beefy desktop pays the round-trip via the hub. Acceptable on Tailscale (typically same-LAN or close); not acceptable for cross-continent hubs.
- Hub is a SPOF for browser access. When the hub is down, no `/web`. CLI is unaffected.
- Peers must accept inbound SSH from the hub. Already true for any peer the hub joined via, but if a peer was joined via someone else, it may not have the hub's pubkey in `authorized_keys`. v0.3 gossip should have wired this; the heal pass (v0.4) makes it more reliable.
- Self-signed cert means a click-through the first time. Users on a public network deserve a real cert; we'll document Tailscale Serve as the easy upgrade path for users who already have it.
- ttyd is an external binary. Install isn't bundled. `nagent web serve` errors with a clear install hint if ttyd is missing on the peer.

### Neutral

- The hub is opt-in. If you don't want one, don't run one. CLI + mesh trust continue to work unchanged.

## Alternatives Considered

- **Per-node HTTPS + Tailscale Serve (no hub).** What the original research recommended. Each node runs its own server, browser is redirected to the owning node. Cleanest in pure-Tailscale environments. Rejected for v0.4 because (a) hard-requires Tailscale on every node, (b) every node ends up managing its own cert, (c) browser switches origin per session which is jarring UX. Kept as a future optimization for Tailscale-heavy setups.
- **Central gateway with peer push (VS Code Remote Tunnels pattern).** Hub accepts persistent outbound WebSockets from peers. Rejected for the SPOF + always-on connection cost reasons above. Reserved for v0.5 if NAT'd peers become common.
- **WebRTC data channels.** Browser ↔ peer direct, hub only does signaling. Rejected: WebRTC adds STUN/TURN, signaling state, and codec gymnastics for a problem Tailscale already solves.
- **Build our own xterm.js + ws server in TypeScript instead of using ttyd.** Rejected: ttyd already implements multi-client, readonly mode, ZMODEM, sixel, perfect terminal resizing. Reimplementing burns implementation budget that's better spent on the multi-host integration.
- **`tmux pipe-pane` + plain text streaming (extending the v0.3 `--line` approach to the browser).** Rejected: kills cursor positioning, colors, alt-screen — anything that's not flat shell output renders garbage.
- **asciinema ALiS protocol + asciinema-player.** Beautiful for read-only / replay. The protocol runs a server-side VT100 emulator so late joiners see the *current* screen state. Defer to v0.5 as a **second mode** (`/web --record`) for share-screen and time-machine scenarios.

## Implementation phases

1. **v0.4.0** — hub + ttyd-per-WebSocket + SSH-Unix-socket-tunnel. `nagent web serve`, `web trust`, `web token`, `web sessions`, `web stop`. Self-signed cert, HMAC tokens. ttyd as a soft dep.
2. **v0.4.1** — install-script tweaks for ttyd on macOS / Linux / WSL. README docs.
3. **v0.5** — asciinema-mode (read-only recording + replay) as a second WebSocket protocol on `/ws/<node>/<name>?mode=record`.
4. **v0.5+** — push-mode for NAT'd peers; per-node HTTPS path for Tailscale-heavy nets; OIDC behind a reverse proxy.
